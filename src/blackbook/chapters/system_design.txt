SYSTEM DESIGN

The system design of Cleanlytics defines how the different modules work together to process data from initial upload to analysis, visualization, reporting, and export. The system follows a modular architecture in which the frontend communicates with the backend through REST APIs. DuckDB is used for analytical data processing, while Supabase is used for authentication and application-level data management.

4.1 BASIC MODULES

The Cleanlytics system is divided into interconnected modules that support the complete data analytics workflow.

Authentication & Security Module

- Provides secure user sign-up and login using Google OAuth 2.0.
- Uses JWT-based authentication for secure API communication.
- Manages authenticated user sessions.
- Supports a local workspace mode for development when authentication is not configured.

Data Ingestion Module

- Allows users to upload datasets in CSV, TSV, TXT, Excel, and Parquet formats.
- Validates uploaded files before processing.
- Uses DuckDB for CSV, TSV, and Parquet data ingestion.
- Uses Pandas for processing Excel workbooks and extracting individual sheets.

Data Profiling & Quality Module

- Analyses the structure and quality of uploaded datasets using DuckDB.
- Calculates row counts, missing values, distinct values, and statistical measures.
- Generates a Data Quality Score based on completeness, uniqueness, consistency, and validity.
- Classifies columns into semantic roles such as Measure, Dimension, Category, Date, Identifier, and Location.
- Provides quality findings and recommendations.

Data Cleaning Module

- Identifies and handles common data-quality problems such as missing values, duplicates, blank cells, whitespace, inconsistent cases, incorrect data types, and outliers.
- Provides cleaning operations such as missing-value imputation, whitespace trimming, case normalization, duplicate removal, outlier removal, column removal, and type conversion.
- Creates snapshots before data-changing operations to support undo functionality for recent operations.

Data Transformation Module

- Prepares cleaned data for further analysis.
- Supports column renaming, splitting and merging columns, date-part extraction, calculated columns, row filtering, and group-by aggregation.
- Allows users to perform transformations through the interface without directly writing SQL queries.

Semantic Model & Relationship Module

- Identifies possible relationships between tables using data-driven containment analysis.
- Determines relationship direction and cardinality using value coverage and column characteristics.
- Classifies tables as Fact, Dimension, Bridge, or Standalone where applicable.
- Builds a JoinGraph for multi-table analysis.
- Allows users to approve, reject, or manually create relationships.

Project Management Module

- Organizes datasets, relationships, operations, and dashboard configurations within individual projects.
- Provides Create, Read, Update, and Delete (CRUD) operations for projects.
- Maintains an isolated DuckDB database for each project.
- Stores application-level project information through Supabase.

Dashboard & Visualization Module

- Provides interactive dashboards for analysing processed data.
- Supports KPI cards and different visualizations such as Bar, Line, Area, Pie, Donut, Treemap, Radar, Funnel, Scatter, Radial Bar, Geographic Map, and other analytical views.
- Provides an Auto Dashboard that selects suitable metrics and visualizations based on the available data.
- Allows users to customize dashboard layouts and widgets.

Report Generation Module

- Generates executive-style business reports from the processed and analysed data.
- Includes dataset summaries, key statistics, analytical findings, and data-quality information.
- Allows users to specify report details such as title, organization, and author.
- Provides print-optimized output that can be saved as a PDF.

Data Export Module

- Allows users to export cleaned and transformed datasets.
- Supports CSV, Excel, JSON, and Parquet formats.
- Uses DuckDB-based export operations to generate the required output files.
- Provides downloadable results for individual project datasets.


4.2 DATA DESIGN

Cleanlytics uses a dual-database architecture. Supabase is used for authentication and application-level data such as users, projects, dashboard configurations, and report information. DuckDB is used for storing and processing the actual uploaded datasets within project-specific analytical databases. This separation keeps application data and analytical data independent and supports efficient data processing.

4.2.1 SCHEMA DESIGN

The data design consists of two parts: the Supabase application schema and the DuckDB analytical schema.

A. Supabase Application Schema

Supabase stores the persistent application information required to manage users and projects.

Table 1: Users / Authentication

Stores user authentication and profile information.

Field	Description
User ID	Unique identifier of the user
Email	User email address
Name	User display name
Authentication details	Information required for user authentication

Table 2: Projects

Stores project and workspace information.

Field	Description
Project ID	Unique identifier of the project
User ID	Identifies the project owner
Project Name	Name assigned to the project
Description	Optional project description
Created At	Project creation timestamp
Updated At	Last modification timestamp

Table 3: Dashboard Configuration

Stores saved dashboard information.

Field	Description
Dashboard ID	Unique dashboard identifier
Project ID	Associated project
Widgets	Chart and KPI configuration
Layout	Position and size of dashboard widgets
Updated At	Last dashboard update

B. DuckDB Analytical Schema

DuckDB stores the physical data uploaded by the user. Each project maintains an isolated analytical database containing the project's uploaded tables.

Data Component	Description
Raw Tables	Original uploaded dataset tables
Profile Information	Column statistics, data types, null counts and distinct values
Cleaned Data	Dataset after cleaning operations
Transformed Data	Dataset after calculations, filtering, splitting, merging and summarisation
Relationships	Detected or user-defined table relationships
Snapshots	Previous table states used for undo operations
Operation History	Record of data-processing operations

4.2.2 DATA INTEGRITY AND CONSTRAINTS

Cleanlytics maintains data integrity through the following mechanisms:

- User and project isolation: Application data is associated with the authenticated user and project.
- Project isolation: Each project uses its own DuckDB database, preventing accidental mixing of datasets between projects.
- Referential relationships: Project-related records are associated with their corresponding project.
- Unique identification: Users, projects, datasets, dashboards, and relationships use unique identifiers.
- Input validation: Uploaded files and API requests are validated before processing.
- Relationship validation: Detected table relationships include confidence and coverage information and can be reviewed by the user.
- Operation safety: Snapshots are created before destructive data operations, allowing recent changes to be undone.
- Authentication and access control: Supabase Authentication and Row Level Security help restrict access to authorized application data.

4.4 SECURITY ISSUES

Security Issue	Description	Counter-Measure Implemented
Unauthorized Access	Users may attempt to access another user's data or projects.	JWT-based authentication protects API endpoints, and requests are scoped to the authenticated user.
Session Hijacking	A stolen authentication token could be used to impersonate a user.	JWT expiration is enforced and tokens are transmitted through the Authorization: Bearer header over HTTPS.
Cross-Origin Attacks	Untrusted websites may attempt to access the backend API.	CORS is configured with explicitly allowed frontend origins.
File Upload Attacks	Users may upload unsupported, oversized, or potentially unsafe files.	File extensions, MIME types, and file size are validated before processing.
SQL Injection	Malicious input could affect dynamically generated DuckDB queries.	User inputs are validated and sanitized, while identifiers are safely quoted and query parameters are controlled.
Data Loss	Failed cleaning or transformation operations may affect the dataset.	Automatic DuckDB snapshots are created before destructive operations, allowing recent changes to be undone.
Cross-Project Data Leakage	Data from one project could potentially be accessed through another project.	Each project uses an isolated DuckDB database, and API access is checked against the authenticated user's project ownership.
Invalid API Requests	Malformed requests may cause unexpected application behaviour.	API inputs are validated using Pydantic models before processing.
Incomplete File Uploads	A failed large-file upload could leave partially processed data.	Files are first written to temporary storage and are processed into DuckDB only after successful upload and validation.
