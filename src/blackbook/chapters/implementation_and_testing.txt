CHAPTER 5: IMPLEMENTATION AND TESTING

5.1 IMPLEMENTATION APPROACH

Project Summary

Cleanlytics is an end-to-end Data Analytics and Business Intelligence platform developed to simplify the process of preparing, analysing, visualising, and reporting data. The system accepts raw datasets and processes them through data ingestion, profiling, quality analysis, relationship discovery, cleaning, transformation, semantic querying, dashboard generation, reporting, and export.

The system is implemented using a Next.js and React frontend with a FastAPI backend. DuckDB is used for analytical data processing, while the application metadata and authentication layers are handled separately. The frontend communicates with the backend through REST APIs.

The complete implementation follows the workflow:

Upload Dataset -> Profile & Quality Analysis -> Clean Data -> Transform Data -> Relationship / Semantic Analysis -> Dashboard & Visualization -> Business Report -> Export Results

The system supports CSV, TSV, TXT, Excel, and Parquet datasets. Uploaded data is processed as project-specific DuckDB tables. Cleaning and transformation operations are performed on the data, while the semantic layer supports relationship discovery and multi-table analysis.

5.2 CODING DETAILS AND CODE EFFICIENCY

Cleanlytics follows a modular coding approach in which different responsibilities are separated into individual modules. The backend is implemented using Python, FastAPI, and Pydantic, while the frontend uses Next.js, React, TypeScript, and related UI libraries.

The main coding areas include:

- Data & Query Processing: DuckDB-based ingestion, querying, profiling, and analytical processing.
- API Layer: FastAPI REST endpoints for communication between the frontend and backend.
- Data Operations: Modules for cleaning, transformation, aggregation, and relationship analysis.
- Metadata Management: Management of projects, tables, relationships, and other application information.
- Authentication: User authentication and JWT verification.
- Frontend Components: Separate components for upload, cleaning, transformation, dashboard, and report generation.

The modular structure makes the system easier to maintain, debug, extend, and test. Reusable functions and components are used wherever possible to avoid unnecessary duplication.

5.2.1 CODE EFFICIENCY

Code optimization was performed to improve execution speed, memory usage, response time, and overall system performance. The following techniques are used:

- SQL Pushdown: Analytical calculations are performed directly in DuckDB instead of processing every row through Python.
- Batch Processing: Profiling operations are divided into manageable batches to control query size.
- Bounded Data Retrieval: Only the required results are returned to the frontend instead of transferring complete datasets.
- Efficient Relationship Discovery: Distinct values and containment analysis are used to reduce unnecessary table comparisons.
- JoinGraph-Based Querying: Valid relationship paths are used for multi-table queries, reducing incorrect joins and fan-out.
- Snapshot-Based Undo: Snapshots allow previous states to be restored without re-processing the original dataset.
- Memory Control: DuckDB configuration and controlled query processing help manage memory usage during analytical operations.

These techniques reduce unnecessary data movement and computation while improving the efficiency of dataset processing and analytical queries.

5.3 TESTING APPROACH

Testing was performed to verify the correctness, reliability, and integration of the major CLEANYTICS modules. Testing covered dataset ingestion, profiling, data-quality analysis, cleaning, transformation, relationship discovery, semantic querying, visualization, dashboard generation, reporting, and export.

Different datasets were used, including datasets containing missing values, duplicate records, inconsistent values, outliers, and normally formatted data. The actual results were compared with the expected results to verify functional correctness.

The testing was divided into:

- Unit Testing: Verification of individual functions and operations.
- Integration Testing: Verification of communication between connected modules.
- System Testing: Verification of the complete application as an integrated system.

5.3.1 UNIT TESTING

Unit testing was performed on individual functions and components before integration. The major areas tested were:

- Data Ingestion: Verified supported file formats, file validation, table creation, and dataset loading.
- Data Profiling: Verified row counts, column information, null counts, distinct values, and statistical calculations.
- Data Cleaning: Tested missing-value imputation, duplicate removal, whitespace trimming, case normalization, type conversion, and outlier removal.
- Data Transformation: Tested date-part extraction, calculated columns, column splitting and merging, filtering, renaming, and aggregation.
- Relationship Analysis: Verified containment calculation, relationship direction, cardinality, and confidence scoring.
- Semantic Querying: Verified query generation, aggregations, filtering, and multi-table joins.
- Visualization: Tested KPI cards and supported chart types using different dimensions and measures.
- Export & Reporting: Verified generation of processed datasets and business reports in the supported output formats.

Unit testing helped identify errors within individual operations before they affected the complete application.

5.3.2 INTEGRATION TESTING

Integration testing verified the interaction between the major components of CLEANYTICS.

The following integrations were tested:

- Frontend to REST API: Verified that user actions generate valid API requests and receive the expected responses.
- REST API to FastAPI: Verified request routing, validation, authentication, and backend processing.
- FastAPI to DuckDB: Verified dataset ingestion, SQL execution, cleaning, transformation, and analytical queries.
- Profiling to Data Quality: Verified that profiling results are correctly used to identify quality issues and calculate quality information.
- Relationship Discovery to Semantic Querying: Verified that detected relationships and the JoinGraph are used for valid multi-table queries.
- Semantic Querying to Dashboard: Verified that query results are correctly mapped to measures, dimensions, KPIs, and charts.
- Processed Data to Reporting & Export: Verified that the latest processed data is used for report generation and data export.
- Authentication to Project Access: Verified that authenticated users can access only their permitted project resources.

Integration testing ensured that data and control flow correctly between the connected modules.

5.3.3 SYSTEM TESTING

System testing was performed on the complete CLEANYTICS application to verify its overall functionality and behaviour.

Testing covered:

- Authentication and protected application access.
- Upload and validation of supported datasets.
- Dataset profiling and quality analysis.
- Cleaning and transformation operations.
- Snapshot-based undo functionality.
- Multi-table relationship discovery.
- Semantic querying and aggregation.
- Dashboard and visualization generation.
- Business report generation.
- Data export in supported formats.
- Project creation, retrieval, and deletion.
- Handling of invalid inputs and processing errors.
- Consistency of processed data across the application.

The system was tested with both normal and problematic datasets to verify that expected results were produced and that invalid operations were handled appropriately.

Overall, system testing confirmed the functional integration of the major CLEANYTICS components and verified that the implemented modules operate correctly as a complete analytics application.

5.4 MODIFICATIONS AND IMPROVEMENTS

During the development of Cleanlytics, several modifications were made to improve data processing, security, usability, and analytical capabilities.

5.4.1 ANALYTICAL DATA STORAGE

The initial implementation stored uploaded data as JSON in SQLite. This was changed to a separate architecture where DuckDB handles the actual analytical dataset, while application metadata remains separate. Each project uses its own DuckDB database, improving analytical processing and data isolation.

5.4.2 AUTHENTICATION AND SECURITY

Authentication was migrated to Supabase Authentication, providing JWT-based sessions and server-side token verification. Project ownership checks were also strengthened so that project and table resources are accessible only to the authenticated user.

5.4.3 MULTI-FILE DATASET SUPPORT

The upload module was modified to support multiple files within the same project. This allows related datasets to be stored as separate tables and analysed together. Excel worksheet support, duplicate-file detection, and upload progress tracking were also added.

5.4.4 SEMANTIC DATA PROFILING

The profiling system was enhanced from basic database-type detection to semantic classification of columns into roles such as Measure, Dimension, Time, Identifier, Geographic, Category, Boolean, and Text. Additional statistical information is also generated to support subsequent analysis and dashboard generation.

5.4.5 SNAPSHOT-BASED UNDO

A snapshot-based undo mechanism was introduced for data operations. Before destructive changes, the current table state is saved, allowing recent operations to be reversed. Up to five recent snapshots are maintained along with operation history.

5.4.6 DATA-DRIVEN RELATIONSHIP DETECTION

Relationship detection was improved by comparing actual column values and containment rather than relying mainly on column uniqueness. The system evaluates relationship direction and confidence, improving the reliability of multi-table analysis.

5.4.7 SEMANTIC DASHBOARD GENERATION

The dashboard was changed from using hardcoded example content to using the semantic information generated during profiling. It can identify measures, time columns, and categorical dimensions to generate relevant KPIs, charts, breakdowns, and leaderboards.

5.4.8 SERVER-SIDE TRANSFORMATION

Data transformation execution was moved to the backend, with the frontend sending the selected operation to the applyOperation API. The backend performs the operation and returns the updated result, ensuring that the displayed result represents the actual server-side processing.
